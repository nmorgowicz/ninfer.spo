- `python -m tools.convert.gemma4_build` builds a Gemma 4 31B 4-bit `.ninfer` in one command from a BF16 checkpoint: five presets (`best-small` GPTQ g256, `best-medium` GPTQ g32, `lite-medium` calibrated RTN g32 with 6-bit scales, `lite-small` calibrated RTN g256, `draft` uncalibrated g32) map to the measured recipes and run the calibration text, the `tools/gptq/` route or llama.cpp statistics, and `gemma4_q4 convert`. The `best-*` presets are the recommended ones (GPTQ, about 30 minutes on an RTX 5090); `lite-*` is for machines that cannot run GPTQ (less RAM and VRAM, no GPTQ environment) and scores lower. It runs a preflight first (`--check`: GPU and VRAM, RAM, disk, GPTQ and llama.cpp environments, model and assistant, server binary and DLLs, each failure with its next action), prints the plan with a time estimate per step (`--dry-run` writes nothing), asks before starting (`--yes`), resumes from per-step done-markers in the work directory (a work directory made with other arguments is refused), never overwrites an output and removes only its own work directory after success. Without `--calibration-text` it downloads the pinned public English corpus the measured numbers used (eaddario/imatrix-calibration at revision `e87ed55dcba9`, sha256-checked) and exports it byte for byte as the author's calibration file. The deliverables are `<name>.ninfer`, the converter receipts, `serve-<name>.cmd` and `BUILD-SUMMARY.md`. `--score` optionally runs the paired-KL check of section 6 of `docs/gemma4-31b-conversion-technical.md`. `setup-gptq --venv DIR` creates the pinned GPTQ environment with uv and verifies its versions; `launcher --artifact F --out F.cmd` writes the Windows server launcher with the qualified settings (131,072 context, FP8 KV, one lane, prefill chunk 128, MTP and vision detected from the artifact). - `gemma4_q4 convert --gptq-source DIR` imports an external LLM Compressor GPTQ checkpoint (compressed-tensors `pack-quantized`, symmetric INT4, static contiguous groups, no activation order; group size 32, 128 or 256) into `q4_g32_fp16` without re-rounding: codes and scales are copied word for word, every scale must convert to binary16 unchanged, zero points and `weight_g_idx` are refused, and the converter's global-layer permutations (q/k rows, o columns) are applied to the encoded words. With `--native-groups` a 128/256 checkpoint is stored in the real `q4_g128_fp16`/`q4_g256_fp16` formats (decoded values identical to the repeated-scale g32 emulation); the ten global-layer o projections, whose column permutation splits a source group, stay `q4_g32_fp16` with the repeated scale (+41 to 48 MB). `tools/gptq/` holds the pinned environment, calibration/tree/GPTQ scripts and a README for producing the checkpoint (`imatrix_mse` observer recommended; the default observer is worse than calibrated RTN). Measured on the calibrated 31B (diode s15 t005, text-only, 47 paired windows, KL A16 / W4A8): GPTQ g32 0.0805 / 0.0845 against 0.1504 / 0.1569 for calibrated RTN g32 (ΔKL -0.070 / -0.072, 46 of 47 windows better); GPTQ g128 0.1033 / 0.1081 (16.59 GB) and g256 0.1192 / 0.1213 (16.37 GB, 1.55 GB smaller than RTN g32) against 0.2290 / 0.2327 and 0.2358 / 0.2376 for calibrated RTN at the same group sizes; g256 beats RTN g32 by -0.031 / -0.036 (CI -0.046..-0.018 / -0.050..-0.023).

- Gemma 4 `q4_g32_s6_fp16`: the same signed 4-bit codes as `q4_g32_fp16` with a two-level scale plane. Per row and per 256 columns one 8-byte block holds a binary16 super scale `S` and eight 6-bit multipliers `m_j`; group `j` is scaled by `fp16_round_nearest_even(float(S) * m_j)`, so the format decodes bit for bit like a `q4_g32_fp16` artifact that stores those scale words. The scale plane is one byte per 32 weights instead of two (4.25 logical bits per weight against 4.5). Layout `row_split_k128_v1`, code planes unchanged; K padded to 128 must be a multiple of 256 (checked in the layout, `encoded_size` and the loader). `.ninfer` v3 and every existing format are unchanged. Kernels, embedding gather and the W4A8 routes decode the plane through one shared helper (`src/ops/common/q4_scale_mode.h`) and pin it with the golden block `55 35 40 20 0c bf ff 45` (S = 0x3555, m = 0,1,2,3,63,62,31,17 gives scale bits `0x0000 0x3555 0x3955 0x3c00 0x4d40 0x4d2a 0x492a 0x45aa`). `python -m tools.convert.gemma4_q4 convert --scale-bits 6 --native-groups` (with `--scale-search mse|weighted`, `--group-size 32`, `--weights q4_g32` or `q4_g32_a16`) stores it: the converter derives `S` and `m_j` from the scale-bits-6 search result, refuses any block whose decoded scales are not bit-identical to it, and zeroes the scales of wholly physical padding groups. The recipe name ends in `_native_scale6` and the receipt's `weight_bytes`/`projected_real_weight_bytes` are the real size. Other `--scale-bits` values, or 6 without `--native-groups`, stay the emulated screening path on ordinary g32 words. Binaries built before this commit cannot load the files.

- `q4_g32_s6_fp16` measured on the calibrated 31B (diode s15 t005, weighted search, text-only): 915,210,240 bytes (5.1%) smaller than the same recipe in `q4_g32_fp16`; the A16 KL run reproduces the `--scale-bits 6` emulation bit for bit (47 windows, identical `kl_sum` and `kl_positions.f32`, mean KL 0.14897 against 0.1504 for FP16 scales); W4A8 with `NINFER_Q4_EXACT=1` scores 0.1543 (g32: 0.1569, paired difference not resolved). Kernel cost against g32 on cold weights (medians): the T=1 GEMV and the A16 tensor-core and wide kernels are within 3% (mostly faster, the plane is 6% smaller); the fused W4A8 prefill GEMM at T=128 is 1-3.5% slower per projection (the T=9 projection 5376x21504 6% slower); served at chunk 128 a 3,000-token prefill runs at the same speed as g32 and decode 3.4% faster.

- `gemma4_q4 convert --mtp-weights fp8|bf16|q4` stores the MTP assistant's 20 layer projections as FP8 per-row (the default for the q4 weights; it was BF16), BF16 (the old layout) or `q4_g32_fp16` (A16Only; the head and outer projections are untouched). Existing recipe names for MTP builds gain `_mtp_fp8`. On the calibrated g256 31B file (eight greedy prompts x3, FP8 KV, 131k context): `fp8` is 184 MB smaller than BF16 with identical draft acceptance (30.0%), identical text and no speed change; `q4` is 265 MB smaller at 28.8% acceptance. The option is ignored without an assistant; passing it with `--no-mtp` is refused.

- `python -m tools.convert.gemma4_q4` converts, verifies and calibrates a Gemma 4 31B custom model without any outside tooling: `convert` reads the BF16 checkpoint (dense 31B, per-layer global geometry translated, optional MTP assistant) and writes a `q4_g32`/`q4_g32_a16`/`fp8_row` artifact with per-region logical groups 32/64/128/256 (emulated or native `q4_g128_fp16`/`q4_g256_fp16`), absmax, MSE or imatrix-weighted scale search and a `<out>.build.json` receipt (`ninfer.gemma4-q4-build/v1`); `verify --artifact` reads every object and hashes the files; `calibration-text` renders chat-prefixed fixed-length chunks for llama-imatrix. `gguf` is needed only for `--imatrix`, `tokenizers` only for `calibration-text`.

- Gemma 4 `q4_g128_fp16` and `q4_g256_fp16`: signed 4-bit codes with one FP16 scale per 128 or 256 weights (4.125 and 4.0625 logical bits per weight against 4.5 for `q4_g32_fp16`). The code plane is byte-identical in layout; only the scale plane shrinks, so a 31B trunk is about 1.0 GB (g128) or 1.6 GB (g256) smaller. Kernels, embedding gather and the W4A8 routes (fused, baked, exact, `NINFER_Q4_EXACT`, ready-codes) take a scale shift (0, 2, 3) and share one copy of the code indexing; the g32 instantiations are the unchanged shift-0 specialization (136 of 138 g32 kernels match instruction for instruction, the other two differ in the operand order of a commutative `LOP3`/`IADD3`). K padded to 128 must be a multiple of 256 for `q4_g256_fp16`; every Gemma trunk K is. Converter: `grouped_absmax_emulated` and `grouped_mse_search` write the native format when the target is `q4_g128_fp16`/`q4_g256_fp16` with a matching `group_size`, and the same codes and scales into `q4_g32_fp16` (repeated scales) for quality emulation; native and emulated artifacts score bit-identically (KL 0.23579 and 0.23758 for g256 A16 and W4A8 on the diode variant). `grouped_mse_search` chooses each group's FP16 scale by exact squared-error search, optionally weighted by an imatrix importance vector (`tools/convert/quantization/importance.py`). Tests: `tests/convert/test_grouped_absmax_emulated.py`, `test_grouped_mse_search.py`, `test_native_coarse_groups.py`, `tests/ops/linear/test_q4_coarse_a16.cpp`, `test_q4_coarse_a8.cpp`.

- KV-format evaluation kit (`tools/bench/kv_eval/`, documented in `docs/kv-evaluation.md`): a reproducible, model-agnostic way to compare KV-cache and quantization arms against a reference arm on one artifact. It runs `ninfer-spo-perplexity --dump-topk` arm by arm with receipts (binary, artifact and corpus hashes, argv, GPU idle state), analyses the reports and dumps (PPL and ΔPPL, top-1 agreement, truncated top-64 KL, target-token log-probability change, paired window `t`, per-domain and position-bin tables, a same-flags noise floor), derives the chat-template prefix ids from the artifact's embedded template and tokenizer, and provides a needle-in-haystack harness (exact McNemar and Wilson intervals) and a speed client (warmup, unique prompts, pinned sampling, median of five). The analysis reproduces the published Gemma 4 31B numbers; `tests/bench/kv_eval` checks it against hand-computed values. The documentation records the 31B BF16, FP8, FP8+QK and INT8 results with each number's instrument, the noise floor and the caveats, and lists what a new model must supply. No engine or kernel change.

- `top_k` runs up to 64. Gemma 4's built-in default is now temperature 1.0, top_k 64, top_p 0.95 (it was top_k 20), and `docs/serving.md` no longer says the suggested 64 cannot be sent. HTTP (OpenAI chat, Responses, Anthropic), `--top-k` of the server and the CLI, and the `ops::sample` and `ops::speculative_accept_greedy_drafts` sampling kernels all accept 1..64; top_k 0 means the model's default top_k (20 for Qwen3.5 and Flash-Next, 64 for Gemma 4). Sampled MTP rounds truncate to the exact top-k at every verify column, for the accept test and for the residual.
  - Qwen3.5 and Flash-Next keep their ceiling of 20 (`ModelSamplingDefaults::max_top_k`): their programs run only the original 20-wide sampling kernels, and the DFlash2 sparse accept reads at most 32 candidates per warp. A larger request is a 400 on `top_k` (and `--top-k` above the loaded model's ceiling stops the server at startup).
  - The sampling ops take `top_k_capacity` (`kSamplingFastTopK` 20, the default, or `kSamplingMaxTopK` 64) on both the workspace query and the launch. The 20-wide instantiation is the original pipeline: same registers and shared memory (`cuobjdump --dump-resource-usage`: 29/60/60 registers for partial, group and single-block kernels) and no timing change beyond noise on a shared GPU. The 64-wide pipeline sorts 8 keys per thread in its group stage (2048-key tiles, 32 partials per group) so one final merge still covers vocabularies up to 524,288 tokens, and falls back to a streamed tile merge beyond that or above 16 columns. Gemma 4 picks the width per request (top_k above 20 selects the 64-wide kernels and recaptures its sampling graphs when the width changes).
  - `ninfer_sampling_select_bench --top-k 1..64 [--wide]` times both pipelines. On the 248,077-token domain (shared GPU, median of three interleaved runs): B=1 stochastic 33 µs at top_k 20 and 38 µs at top_k 64; MTP K=5 44 µs and 77 µs.
- Opt-in, quality-unqualified Gemma 4 global-layer `--kv-dtype int8`: INT8 codes
  with one FP16 scale per 64 elements (eight per D512 K/V vector, 42,240
  B/token for the 31B geometry). Sliding rings, snapshots and vision stay BF16;
  BF16 remains the default and FP8 behavior is unchanged. Target and MTP
  attention dequantize to BF16 on read (SIMT and tensor-core staging); there
  is no INT8 tensor-core path and no rotation. `--gemma4-qk fp8` with
  `--kv-dtype int8` is rejected. All four global code/scale planes are
  registered with checkpoints, copy-on-write and host capture/restore;
  capacity sizing, startup/request-log fields and perplexity treat INT8 like
  FP8.

- Opt-in Gemma 4 `--gemma4-qk fp8` enables global D512 FP8 tensor-core QK
  for query widths ≥64 with FP8 KV storage. Two transient FP16-rounded Q
  scales match K's 256-element grouping; each FP32 partial is corrected
  separately before summation. BF16-expanded V and hi/lo BF16 PV, sliding
  D256 and short SIMT remain unchanged. `--gemma4-qk bf16` remains the
  default and the Phase 1 comparison path. CLI, serve and perplexity report
  selection/scope; incompatible architecture/cache combinations fail closed.
  This changes runtime computation, not artifact conversion or model-quality
  qualification.

The comparison table is in the README.
- Gemma 4 keeps prompt checkpoints (`prefix_store.h`, `prefix_cache.h`). Global-layer KV is a pool of reference-counted 64-token pages shared between the live sequence and checkpoints, copied only when the live sequence writes a shared page. Each checkpoint snapshots the sliding ring's last 21 pages into one of `--device-state-slots` device slots, and the least recently used one moves to the pinned `--host-context-mib` arena (default 8 GiB) or is dropped. Captures happen at the end of the leading system turn, at explicit `prompt_cache_breakpoint` markers (prefill chunks split there; the server's automatic last-message boundary is ignored), and of the live state before a request overwrites at least 256 of its tokens. A checkpoint replaces the live state only when it saves at least 256 prompt tokens, or 1,024 from the host. A prompt that extends a checkpoint marks it used, and the checkpoint a request restores is never the one evicted to make room for the state it displaces (that eviction failed a long session replay with "prefix store lost a checkpoint"). Image positions are keyed by an image hash, so image prompts reuse too, and a fully reused image is not encoded again. A voice turn after a summary, an image, and a manual-chat request reuses 2,462 of 2,499 prompt tokens. A memory-message change resumes from the system-plus-tools frontier. Both produce the same tokens as a fresh prefill. A recorded 62-request voice session computes 26.0k of 484k prompt tokens, with a median TTFT of 104 ms. Tests `ninfer_gemma4_prefix_store_test` and `ninfer_gemma4_checkpoints_real_test`.
- A Gemma 4 prompt longer than `--max-context` is a context-length error (HTTP 400), not an internal error (500).
- Gemma 4 MTP also runs for sampled requests (temperature above 0 or a penalty). Each draft is accepted with its target probability and the correction is drawn from the residual (`ops::speculative_accept_greedy_drafts`), in the same round graph. 300 seeded short samples match plain decode's opening frequencies. At temperature 1.0 (top_k 20, top_p 0.95), 256-token chat replies decode at 133 tok/s median on the 31B FP8 A8 artifact, against 46 without MTP, and `auto` stays at 6 drafts. On a recorded voice session (replies of 20–100 tokens) 4 drafts was fastest, 87 tok/s against 80 at 6; the time to the first token was 67 ms at every draft count.
- Gemma 4 supports `tool_choice` `required` and a named function: the tool-call opener is appended to the prompt, and the output session starts inside the call and rejects undeclared names. Stop strings work like Qwen's, within one output channel.
- `tools/smoke/serve_gemma4_voice.py` checks a Gemma 4 server for voice chat over HTTP (prewarm, SSE with timings, developer, tool_choice, tool results, image_url, breakpoints, cancel, context length). `docs/serving.md` has a Gemma 4 section with the launch line and checkpoint sizing.
- Gemma 4 QAT text projections can be stored as `q4_g32_fp16` (signed 4-bit codes, groups of 32, one FP16 scale). `q4_g32_qat` recovers the scale already in the checkpoint instead of quantizing it again. Recipe `gemma4_31b_q4_qat`, override `gemma4_q4_a8`. Decode uses a bandwidth GEMV (1.45–1.53 TB/s from DRAM) and MTP verify an 8-token tensor-core GEMV. With `AllowA8`, the trunk shapes run W4A8 from 9 tokens: each group's codes become E4M3 under one BF16 multiplier per row (stored at load, 2 bytes per row), so the FP8 A8 tiles do the multiply. 9–384 tokens convert the codes inside the GEMM, 385 and up convert once per call into a workspace and reuse the FP8 A8 kernels. On the RTX PRO 6000, 31B decode is 67.5 tok/s (FP8 44.4), a 17-token prompt prefills in 19 ms instead of 51 ms, and 4096 tokens in 681 ms. KL against the QAT BF16 checkpoint is 0.0089 at context 4096 and 0.0107 at context 384, where every prefill takes the fused route (exact q4 prefill 0.0056 and 0.0063, `NINFER_Q4_EXACT=1`); GSM8K-200 is 98.5%. q4 never goes through `fp8_row_cublas`. MTP acceptance on ShareGPT prompts is low with the q4 target (length 1.95 against 6.74 on FP8) and is not investigated.
- Gemma 4 FP8 trunk projections with A8 (`gemma4_fp8_a8`) switch to A8 at 33 tokens instead of 128. Below 128 tokens the 5376-row shapes use a 32×64 tile up to 64 tokens and a split-K 64×128 tile above; the wide shapes use 64×128. TTFT of a 64-token prompt drops from 40.0 to 25.3 ms, 96 tokens from 56.7 to 33.2 ms, 127 tokens from 61.5 to 34.4 ms; 32 tokens and 128 and up are unchanged. KL at context 96 against BF16 is 0.0193, against 0.0106 with A16 only.
- Gemma 4 FP8 and NVFP4 recipes store one FP8 vocabulary table: the embedding binds the head's unscaled object, and the gather multiplies each row by the BF16 √hidden normalizer (`ops::embedding` with a scale), as Hugging Face does. The 31B artifact is 1.4 GB smaller and loads one copy. Artifacts with two tables still load. KL at context 96 is unchanged (0.0195 against 0.0193).
- Gemma 4 vision attention is one tensor-core flash kernel with FP32 softmax weights and no T² buffers. A 2,520-token image encodes in about 40 ms instead of about 500 ms. The encoder no longer syncs per padded GEMM, and patch scaling, RoPE tables, and pooling run on the GPU. `gemma4_vision_encode` returns before the embeddings are ready; `Program::encode_vision` syncs the stream first. Without that sync a red image was described as white.
- Gemma 4 FP8 trunk projections at 17 to 127 tokens have their own routes (`shapes/gemma4_a16.cu`). The new `fp8_a16_wide_gemv` kernel gives each CTA 32 or 64 rows and is 23–35% faster at 32 tokens and 34–60% faster at 48 than the generic route. A 32-token prompt's TTFT on `gemma4_31b_fp8_a8` drops from 33.9 to 25.4 ms. Decode and MTP verify (at most 16 tokens) are unchanged.
- Gemma 4 `--draft-tokens auto` drafts 6 tokens per round instead of 5: +4.9% decode on a code and docs corpus and +11.6% on ShareGPT at 4k context.
- `ops::topk_columns` merges with 1024 threads per column (about 13 µs instead of 650–745 µs on a 262,144-row column). It has a total order for NaN (a NaN at row 0 first, other NaNs after every number) and writes -1 for ranks past `valid_rows`.
- Gemma 4 vision attention no longer uses cuBLAS. The dots and the value multiply are ours, and the softmax between them is unchanged. The encoder's registered BF16 projections, including each half of gate/up, run on the BF16 tensor-core kernels.
- `Bf16GemmContext` takes no cuBLAS workspace unless the caller asks for one. The 64 MiB buffer changed the summation order and moved the Flash-Next greedy prefix and the Gemma bf16 parity.
- Gemma 4 text prefill of 32, 64, 128, 256, 512, and 1024 tokens runs as one CUDA graph (`prefill_graphs.h`). Vision chunks stay eager.
- Gemma 4 FP8 A8 uses a 64-token tile at 128 tokens and a 128-row tile up to 512 tokens, where those beat the 128×256 bulk tile.
- Gemma 4 GeGLU can write the down projection's E4M3 codes in the same kernel, and the down GEMM then skips its own quantize (`ops::linear_a8_ready`).
- The Gemma 4 MTP assistant projections are quantized to FP8 at load and run on the dense GEMV.
- Gemma 4 31B-it is a third family (`Gemma4ForCausalLM`): text, the MTP assistant, and the vision tower. The converter is `tools/convert/gemma4.py`. The sliding window stays in the Gemma program ring.
- Flash-Next sizes its checkpoint catalog and KV address stores from the device state slots instead of a fixed 8 records. With `--device-state-slots` above 6 the catalog used to fill first: captures were skipped and finished continuations dropped, while the resource manager saw free slots and reclaimed nothing, so every later request resumed from one old checkpoint. New real test `--many-checkpoints`.
- `scripts/serve.cmd` passes `--device-state-slots 16`. With the default two, Pi sessions fell back to old checkpoints after pi-lens rewrites (TTFT up to 3.4 s), and two chats fell back to the system prompt on every request (`docs/serving.md`, "Flash-Next checkpoint slots").

## base

This tree is ninfer.spo: NInfer's V3 runtime, the Windows layer, and Qwen3.8 Flash-Next and Qwen3.5 on `sm_120a`.

- Binaries `ninfer-spo`, `ninfer-spo-serve`, and `ninfer-spo-perplexity`.
- Shared program storage under `src/program`, one KV page and address store for both families, plus the `Program` declarations, decode graph families, and causal-score staging. Model math stays in the model families.
- Context-cache shared prefixes, with a device state copy so a warm continuation matches a cold one. Thinking turns reuse their history too. Reclaim counts only the pages a release actually frees.
- One request that cannot obtain a unit returns a context-length error (400). The engine keeps serving.
- Image prompts: decode positions carry the image RoPE offset, and prefix reuse compares the image, not only the token ids.
- Pause, replay, and forced tokens map KV before they write it. Penalty counts and MTP counters stay per request across a pause.
- Windows waits, exclusive bind, encode-splice check, and console code page (also restored on Ctrl+C).
- On Linux a second server cannot bind the same port (no `SO_REUSEPORT`).
- Public types split under `include/ninfer/types/`. The agent guide and the operator docs are in `AGENTS.md` and `docs/`.
- `--capture-path` and `--steering-pack` record or steer a request. The record id is `capture.record_id`. Ordinary requests, with neither set, do not create that control.
- An unexpected engine exception finishes every held request and stops the engine. A context-length rejection still leaves the engine up.
- A lost CUDA context, including after sleep, throws instead of aborting, so that same stop path runs.
- `ninfer_bench` takes the host flags and binds to the GPU's NUMA node like the server. Before, it left the 47.68 GiB PLE table wherever Windows put it.
